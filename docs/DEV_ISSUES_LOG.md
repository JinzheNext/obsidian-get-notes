# Get Notes 开发问题记录

这个文件用于持续记录开发过程中遇到的问题、根因、解法和后续优化点。
后续每次出现新的重要信息，都直接追加到这里，避免上下文压缩后遗失。

---

## 2026-05-05

### 1. OpenAPI 连接测试接口不稳定

- 现象：
  `Test connection` 早期调用 `user/profile` 会失败，但 `note/list` 可用。
- 根因：
  Get OpenAPI 的某些接口稳定性与当前凭证可用性不一致。
- 解法：
  把连接测试改成基于 `note/list?since_id=0`。

### 2. 同步失败却显示 success

- 现象：
  出现错误时 UI 仍显示 `success`。
- 根因：
  同步摘要状态判断只看计数器，没有把顶层错误视为失败。
- 解法：
  统一同步结果语义，只要存在顶层错误就标记为 `failed`。

### 3. 历史文件重复生成

- 现象：
  同一条笔记在 Vault 中出现两份甚至多份 Markdown。
- 根因：
  早期 state 持久化异常，`notesById` 和现有文件不一致，导致重新分配序号。
- 解法：
  增加 Vault 扫描与状态回填，按 `note_id` 识别 canonical 文件；
  补了去重脚本，清理历史重复文件。

### 4. 第三方 legacy 导出页路径漂移

- 现象：
  第三方插件登录成功后并没有真正同步。
- 根因：
  原项目依赖的导出页面与按钮选择器已经漂移。
- 解法：
  修复 legacy 导出页 URL、选择器、任务跟踪与下载逻辑；
  已向上游提交最小兼容性 PR。

### 5. 插件偶发“加载失败”

- 现象：
  Obsidian 显示 `obsidian-get-notes 插件加载失败`。
- 根因：
  把 `playwright` 这类重依赖放到了主 bundle 的顶层静态依赖中，导致插件加载阶段就尝试解析浏览器模块；
  某次覆盖 live plugin 时，`main.js` 还一度被写成空文件，进一步放大问题。
- 解法：
  改成只在普通登录/导出真正触发时，按插件目录懒加载 `playwright`；
  新增发布前检查脚本 `scripts/preflight-check.mjs`；
  新增发布清单 `docs/RELEASE_CHECKLIST.md`。

### 6. 普通登录手机号明明 11 位却被拦截

- 现象：
  用户输入真实手机号仍提示“请输入正确的 11 位手机号”。
- 根因：
  正则与输入状态读取逻辑曾有问题。
- 解法：
  修正为真正的 `^\\d{11}$` 判断；
  点击登录时直接读取输入框当前值，而不是只依赖 `onChange`。

### 7. 普通登录模式会报 `Cannot find module 'playwright'`

- 现象：
  登录弹窗点击后，报找不到 `playwright`。
- 根因：
  在 Obsidian/Electron 的运行环境里，模块解析基准不稳定；
  顶层静态依赖和错误的解析上下文都会触发这个问题。
- 解法：
  改成只在普通登录/导出执行时按插件目录懒加载 `playwright`；
  这类依赖禁止在插件加载阶段执行。

### 8. 普通登录模式“点击导出”被官方限流

- 现象：
  在 Get 网页中点击 `点击导出` 会提示“操作太频繁了，请稍后重试”。
- 根因：
  当前导出接口存在频率限制。
- 结论：
  普通登录模式不能默认频繁触发新导出任务。
- 解法：
  普通模式优先复用已有的最近一次导出；
  页面存在 `下载文件` 时，应优先点击下载现成 ZIP，而不是先强行创建新导出任务。

### 9. 普通登录模式误报“下载超时”

- 现象：
  插件提示“下载超时，请稍后重试”，但用户在网页中其实可以点 `下载文件`。
- 根因：
  旧逻辑在创建新导出任务失败后，会尝试自己再请求 `latest=true`；
  但这个接口依赖页面自动携带的 `authorization` 和 `xi-csrf-token`，手动重发容易失败。
- 解法：
  改成优先复用页面加载时已成功返回的最新导出信息；
  更进一步，优先点击页面现成的 `下载文件`，避免再次触发导出限流。

### 10. 普通登录模式导出 ZIP 超过 2 GiB 导致失败

- 现象：
  报错：`File size (3187708083) is greater than 2 GiB`
- 根因：
  不是 Obsidian 限制，而是普通模式使用的 JS 解压库 `decompress` 不适合处理 3GB 级全量 ZIP。
- 结论：
  Get 普通模式导出当前是全量包，3GB 体量是正常现象。
- 解法：
  把 ZIP 解压改成系统级解压器：
  macOS 用 `ditto -x -k`
  其他平台回退到 `unzip`

### 11. 构建产物与 live plugin 不一致

- 现象：
  源码已改为系统解压，但 Obsidian 里实际跑到的还是旧逻辑。
- 根因：
  live plugin 目录中的 `main.js` 没有及时被新的 bundle 覆盖，或覆盖过程出现异常。
- 解法：
  每次修复后都要核对：
  - 源码 `main.js` 中是否包含新逻辑
  - live plugin 目录里的 `main.js` 是否同步更新
  - 如有必要，强制覆盖并重启 Obsidian 验证

### 12. 普通登录模式应优先复用“最近一次导出”

- 现象：
  用户在 Get 网页里可以直接点击 `下载文件` 成功下载最近一次导出，但点击 `点击导出` 会立即提示“操作太频繁了，请稍后重试”。
- 根因：
  普通登录模式最开始仍然把“新建导出任务”当作主路径，与 Get 当前的频率限制策略相冲突。
- 解法：
  调整策略为：
  - 优先读取页面已存在的最近一次导出信息
  - 优先点击页面里的 `下载文件`
  - 只有在没有现成导出时，才尝试创建新的导出任务

### 13. 普通登录模式本质上更像“全量快照导入”

- 现象：
  导出 ZIP 体积约 3.18 GB，且每次导出看起来都是全量数据集。
- 结论：
  普通登录模式不适合按 OpenAPI 的细粒度增量思路来理解，更像“拿一份最新全量快照重新导入”。
- 解法：
  - UI 上明确提醒用户该模式更适合低频同步
  - 同步间隔建议拉长到 180 分钟以上，甚至按天使用
  - 后续如果要做更细的更新统计，需要以本地快照对比为主，而不是假设官网给了真正增量接口

### 14. 普通登录模式需要在 UI 上显式展示登录态与最近导出时间

- 现象：
  用户完成网页登录后，只看到 toast，不确定插件是否真的记住了登录态；下次打开设置页也不知道是否需要重新登录。
- 解法：
  在设置页补充：
  - `登录状态`
  - `最近登录`
  - `最近导出`
  并在登录完成、同步完成后刷新设置页，避免用户误判当前状态。

### 15. 普通登录模式的输出结构需要向 API 模式靠拢

- 现象：
  普通登录模式虽然导出成功，但目录结构和文件命名与 API 模式不一致，不利于用户长期使用和对比。
- 解法：
  统一到与 API 模式接近的结构：
  - 分类目录：`01 语音记录` / `02 多人会议` / `03 纯文本记录` / `04 链接同步摘抄` / `99 其他`
  - 音频、图片、文件统一放到 `_assets`
  - 文档文件名改为与 API 模式一致的序号 + 标题 + noteId 形式

### 16. 部署到 live plugin 后不能只相信覆盖命令成功

- 现象：
  某次重新部署后，live plugin 目录里的 `main.js` 被覆盖成了 `0` 字节文件，Obsidian 直接报“插件加载失败”。
- 根因：
  仅执行复制命令还不够，如果不核对目标文件大小和内容，就可能把部署异常漏过去。
- 解法：
  把“部署后立刻检查 live plugin `main.js` 的大小和内容一致性”加入发布清单。

### 17. 普通登录模式显示“同步进行中”但目录暂时没有变化，不一定是卡死

- 现象：
  用户点击普通登录模式同步后，Obsidian 显示“同步已在进行中”，但 `legacy` 目录里的文件时间短时间内没有变化。
- 排查结论：
  这次实际是在后台下载全量导出 ZIP，而不是彻底卡死。排查时在 Playwright 临时下载目录发现了正在增长的 `.crdownload` 文件：
  - 14:17:55 时约 `1660831391` 字节
  - 14:17:58 时约 `1666778783` 字节
  说明下载仍在持续进行。
- 根因：
  普通登录模式当前会先完整下载约 3GB 的全量导出包，只有下载完成后才会进入解压、清理旧目录、重建分类目录和写入文档阶段。
- 解法：
  产品层面要补充更清晰的阶段反馈，至少明确显示：
  - 正在下载 ZIP
  - 正在解压
  - 正在分类写入
  否则用户会误以为“没有任何变化 = 卡住了”。

### 18. API 模式在纯文本和链接摘抄中存在“智能总结 / 笔记内容”重复渲染

- 现象：
  在 `03 纯文本记录` 和 `04 链接同步摘抄` 中，`智能总结` 与 `笔记内容` 经常几乎相同，导致 Markdown 看起来机械重复。
- 根因：
  旧渲染逻辑没有按笔记类型区分，也没有做“总结与正文重复”的检测。
- 解法：
  - 增加基础文本归一化与重复检测
  - 对纯文本、链接摘抄优先保留 `笔记内容`
  - 只有在 summary 与 content 不重复时，才额外渲染 `智能总结`

### 19. 普通登录模式的“笔记内容”与“智能总结”存在语义错位

- 现象：
  在普通登录模式的一些音频/会议笔记里，`笔记内容` 实际上更像 API 模式中的 `智能总结`，并不是真正的原文转写。
- 根因：
  当前 Legacy HTML 导出里，能稳定拿到的更像总结性文本，而不是完整原文。
- 解法：
  - 对 Legacy 的音频/会议笔记，把这类文本放入 `智能总结`
  - `笔记内容` 明确显示缺失提示
  - 不再把“总结性文本”伪装成“原文内容”

### 20. 用户可见目录名需要产品化

- 现象：
  `openapi/` 和 `legacy/` 这类目录名对开发者友好，但对普通 Obsidian 用户不够直观。
- 解法：
  新的用户可见目录改为：
  - `API 模式/`
  - `普通登录模式/`
  同时保留旧目录：
  - `openapi/`
  - `legacy/`
  旧目录不会自动删除，用于比较和迁移。

### 21. 标题是跨模式匹配的好信号，但不能当唯一主键

- 现象：
  同一条笔记在 API 模式和普通登录模式下，标题经常一致，看起来很适合直接用标题做合并。
- 风险：
  - 同名不同笔记
  - 自动生成标题
  - 标题后续被修改
- 解法：
  把标题降级为“候选匹配信号”，不能单独作为强匹配依据。
  未来需要和创建时间、类型、内容 hash、源 URL、音频指纹等一起使用。

### 22. API 模式是更强的数据源，普通登录模式更适合作为兼容导入路径

- 对比样本：
  - API：`0001-AI使用体验记录与工作流优化设想-1908832548952325264.md`
  - Legacy：`0545-AI使用体验记录与工作流优化设想-394a6191c21df8e149b9485ae347ff03.md`
- 结论：
  API 模式明显字段更丰富，尤其是：
  - 原始转写
  - 智能总结
  - note type
  - 更新时间
- 产品判断：
  普通登录模式不应伪装成与 API 等价，更适合被定位为：
  - 无 API Key 的兼容导入路径

### 23. V5 Final 需要从“双渲染器”切到“单协议”

- 现象：
  API 和普通登录各自维护一套渲染结构时，后续每补一个字段、每修一个边界，都要改两条链路，结果很难长期保持一致。
- 根因：
  系统一开始是按“来源”组织的，而不是按“最终笔记协议”组织的。
- 解法：
  引入 `CanonicalNote` 作为唯一中间模型；
  所有路径、附件、Markdown 渲染、fingerprint、deleted 逻辑都统一基于 `CanonicalNote`。

### 24. `deleted` 状态必须高于同步优先级

- 现象：
  如果用户手动删掉一篇同步笔记，而远端数据还在，传统同步很容易把它又恢复出来。
- 产品风险：
  这会直接破坏用户对插件的信任，尤其是已经开始手工整理 Vault 的用户。
- 解法：
  在同步状态中引入 `deleted` 标记。
  只要 state 存在但文件本地消失，就判定为“用户主动删除”，后续不再自动恢复。

### 25. 真实样本表明 Legacy HTML 在会议类上天然缺正文

- 离线对照结果：
  基于本地 raw-cache 与官方 ZIP，对上了 `521` 组强匹配样本。
- 关键发现：
  `meeting` 类样本中，API 正文长度中位数比 Legacy 可见 HTML 多约 `5945` 字符；
  `local_audio` 多约 `5752` 字符。
- 结论：
  “只来了一部分”的主因仍是 Legacy 可见层不完整，不是单纯渲染错误。

### 26. 那 12 条“没来”的笔记，有一批其实是标题 HTML entity 漂移

- 现象：
  初看有 `12` 条 API 笔记在 ZIP 里找不到对应 Legacy 笔记。
- 深挖后发现：
  其中多条并不是真的缺失，而是 Legacy 标题里保留了 HTML entity，例如：
  - `&#43;`
  - `&#34;`
  - `&lt;`
- 解法：
  增加跨来源标题匹配归一化：
  - 先解 HTML entity
  - 再归一化中英文引号、冒号和空白
  让 API / Legacy 在标题匹配上更稳。

### 27. `data-json` 当前更像黑盒 payload，而不是普通 JSON

- 离线扫描结果：
  当前 ZIP 中 `548` 篇 HTML 都带 `data-json`。
- 但在完整 HTML entity 还原后：
  - 直接 base64 decode 后不是 JSON
  - 常见 zlib/raw-deflate 也解不开 JSON
  - 当前扫描结果是 `0` 篇能直接还原为 JSON 结构
- 结论：
  这更像一层额外封装或加密后的 payload，不是简单压缩。
- 当前策略：
  - 保留显式 `data-json` 解码入口
  - 未知格式直接 fallback 到 HTML
  - 同时优先使用本地 API raw-cache 做补齐

### 28. 普通登录模式的 ZIP 不会无限累积，但临时缓存仍要做保洁

- 当前实现：
  Legacy 导出的 ZIP 固定写到 `~/.get/cache/playwright/get_export.zip`，新同步会覆盖旧 ZIP，不会一版一份无限增长。
- 真正的风险：
  - 异常中断后残留的 `~/.get/cache/data-*` 解压临时目录
  - 长时间遗留的调试截图 `page_screenshot.png`
  - 极老的 ZIP 缓存文件
- 解法：
  在 Legacy 导出开始前增加轻量清理：
  - 清理超过 1 天的 `data-*` 临时目录
  - 清理超过 7 天的截图
  - 清理超过 14 天且未再使用的 ZIP
- 约束：
  不清理 `get_auth.json`；
  不自动清理 API `raw-cache`，避免影响从缓存重建和双源补齐。
  - 备份 / 全量导出路径

### 23. V5 测试现象：API 模式只导入了 1 条，普通登录模式 0 条

- 测试时间：
  2026-05-05，V5 目录命名与渲染语义调整后
- 现象：
  - API 模式新目录 `API 模式/` 下只出现了 1 条文件
  - 普通登录模式新目录 `普通登录模式/` 下没有看到新文件
- 初步判断：
  - API 模式很可能受现有 state / raw-cache / nextLocalSequence / notesById 的历史缓存影响，导致只把“新发现的一条”写进新目录
  - 普通登录模式可能仍在下载全量 ZIP、或仍受旧 bundle / 历史导出缓存 / 新旧目录切换影响，需要继续确认
- 处理策略：
  这不应该直接解读为“新结构完全失败”，更像是：
  - 历史缓存与新目录命名叠加后，当前同步结果没有完整重建
  - 下一步需要重点检查：
    - API 模式是否应该支持“迁移到新用户目录”时强制重建
    - 普通登录模式是否完成了下载、解压、分类写入
    - 旧目录与新目录之间是否存在缓存命中但未触发重写的问题
  - 备份路径

### 23. 纯文本 / 链接摘抄的 API 渲染需要按笔记类型做差异化

- 现象：
  在 `03 纯文本记录` 和 `04 链接同步摘抄` 中，旧 API 渲染经常把同一段内容同时放在 `智能总结` 和 `笔记内容`。
- 根因：
  旧逻辑没有做“summary 与 content 是否重复”的检测，也没有按 note type 做差异渲染。
- 解法：
  - 增加基础文本归一化与重复判断
  - 纯文本 / 链接摘抄优先保留 `笔记内容`
  - 只有 summary 与 content 明显不同时才渲染 `智能总结`

### 24. 普通登录模式的旧 `legacy/notes/...` 目录需要有明确生命周期

- 当前策略：
  暂时保留旧 `legacy/notes/...` 作为历史对照样本。
- 原因：
  - 用于比较旧结构与新结构
  - 用于验证迁移时是否丢内容
  - 用于调试 parser / renderer 差异
- 约束：
  插件不会自动删除它。
  后续如果要清理，应该以报告、归档或用户确认的方式进行。

## 已确认的产品结论

### 普通登录模式

- 更适合非会员用户
- 当前强依赖网页结构
- 导出很可能是全量导出
- 导出存在频率限制
- 自动同步不适合过短周期

### API 模式

- 更适合会员用户
- 稳定性更高
- 更适合做增量更新、重建和长期知识库维护

- 根据最近一次导出时间动态提示用户是否适合再次导出

- 评估普通模式自动同步默认值是否应改为 3 小时或天级别

### 23. OpenAPI 音频附件命名与文稿 stem 不一致

- 现象：
  OpenAPI 模式下，Markdown 文件名已经采用 `序号-标题-noteId`，但音频附件仍然使用 `noteId-序号` 命名，用户在 Vault 里按文件名浏览时不容易把附件和对应笔记直接对应起来。
- 根因：
  音频路径构建仍沿用了早期的 `noteId` 命名方式，没有跟最终的 Markdown stem 对齐。
- 解法：
  将 OpenAPI 模式下的音频附件命名改为与文稿 stem 对齐：
  `序号-标题-noteId-音频序号.ext`
  这样附件与 Markdown 在 Finder 和 Obsidian 中更容易一眼对应。

### 24. OpenAPI “只来了一部分 / 没来”多数不是渲染器丢数据，而是上游字段能力差异

- 排查范围：
  基于当前插件 raw cache 对各 `note_type` 做了字段统计。
- 结论：
  - `audio / meeting / local_audio`：
    `summary.content` 与 `detail.content` 基本一致，`detail.audio.original` 才是完整原始转写。
    这说明 API 本身就是“总结 + 原文转写”双轨字段，不应把 `detail.content` 误当原文。
  - `link / plain_text`：
    很多笔记里 `summary.content` 与 `detail.content` 本质相同，说明这两类在当前 API 中经常只给出一份摘要式或正文式内容，而不是两份语义明确分开的字段。
  - 少量 `plain_text`：
    raw cache 中确实存在 `title / summary.content / detail.content` 全空样本。
    这类“没来”的问题来自上游返回为空，不是 MarkdownRenderer 吃掉了内容。
- 对 V5 的产品含义：
  对用户必须明确区分：
  - “当前 API 提供了摘要和原始转写”
  - “当前 API 只提供了一份内容”
  - “当前 API 没提供可渲染正文”
  不能继续假设所有 note type 的字段语义完全一致。

### 25. Legacy 导出 ZIP 中存在隐藏 `data-json`，当前解析器尚未利用

- 现象：
  每篇 Legacy 导出 HTML 顶部都带有隐藏节点：
  `#jsonData[data-json=\"...\"]`
- 当前状态：
  现有 `LegacyGetCore` 只解析页面里已经渲染出来的 HTML，可稳定拿到标题、标签、音频标签和正文可见文本。
- 新发现：
  页面可见层对音频/会议类更多呈现的是“总结型文本”，看不到与 OpenAPI `audio.original` 对应的完整逐字转写；
  但 ZIP 中又额外携带了隐藏 `data-json` blob，说明普通登录模式很可能还有一层更原始的数据未被利用。
- 当前判断：
  Legacy “只来了一部分”至少有两层根因：
  1. 页面层本身只渲染了总结型内容
  2. 插件尚未解码隐藏 `data-json`
- 下一步：
  继续逆向 `data-json` 的编码/压缩/加密方式；
  如果能解出结构化 payload，Legacy 模式的内容完整度还有明显提升空间。
