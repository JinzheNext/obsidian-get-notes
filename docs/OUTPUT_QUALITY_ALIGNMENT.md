# Output Quality Alignment

这个文档记录 V5 中针对 API 模式与普通登录模式输出质量差异的对齐规则。

## 核心判断

- API 模式是更丰富、更稳定的主数据源
- 普通登录模式是兼容导入 / 备份路径
- 两种模式不应该假装“字段能力完全一样”

## Section 语义约定

### `## 概览`

只放元信息和摘要式概览：

- 类型
- 来源
- 入口类型
- 创建时间
- 更新时间
- 子笔记数
- 附件数

### `## 智能总结`

只放 AI 总结、摘要、高亮、待办这类“总结性内容”。

### `## 笔记内容`

只放原始正文、转写、用户原始输入、摘抄原文。

### `## 原始引用`

放来源 URL、原始链接、外部引用。

### `## 附件`

放音频、图片、文件等附件。

## API 模式规则

### 音频 / 多人会议

- `智能总结` 放总结性文本
- `笔记内容` 放原始转写 / 原文
- 如果没有原始转写，但有总结，则保留总结，并在 `笔记内容` 显示缺失提示

### 纯文本 / 链接摘抄

- 如果 `智能总结` 与 `笔记内容` 本质相同，则优先保留 `笔记内容`
- 不再机械重复渲染两份相同内容

## 普通登录模式规则

### 音频 / 多人会议

普通登录模式导出的 HTML 当前更像“总结性文本”，而不是完整原文转写。

因此：

- 这类内容放在 `智能总结`
- `笔记内容` 显示缺失提示：

`普通登录模式导出的数据中暂未包含完整原文内容。建议使用 API 模式获取更完整的转写内容。`

### 纯文本 / 链接摘抄

- 如果 Legacy HTML 中能拿到真实正文，则放在 `笔记内容`
- 如果拿到的是总结性文本，后续再继续精细区分；当前优先避免把“总结”误标成“原文”

## 已知限制

- 普通登录模式的数据能力仍然受 Get 网页导出格式限制
- 当前 Legacy 对“真实原文 vs 总结文本”的区分仍有继续提升空间
- API 模式字段更完整，跨模式比较时默认应优先信任 API 结果
